# 架构设计文档

## 设计思路
本项目定位为**轻量级桌面RPA工作流**，核心设计原则：
1. **零依赖优先**：不依赖重型运行时（Python/Node.js/Electron），使用系统原生自动化框架
2. **极速响应**：事件钩子级别监听，触发到执行延迟<10ms
3. **稳定可靠**：直接调用系统API，不依赖OCR/图像识别等不稳定方案
4. **配置驱动**：支持任意目标平台，无需修改代码
5. **用户无感**：后台静默运行，菜单栏一键控制，不干扰正常工作

## 模块详细设计

### 1. Chrome扩展复制模块
**文件**：`chrome-extension/src/content.js`
**运行环境**：Chrome Content Script 沙箱

#### 双引擎适配架构：
飞书表格存在两种完全不同的渲染模式，本模块设计了双引擎自动切换架构：

**引擎A：DOM 引擎（多维表格 bitable）**
- 适用场景：飞书多维表格（/base/、/bitable/），单元格为独立 DOM 节点
- 核心算法：特征匹配 + DOM 向上溯源
- 从点击元素向上遍历最多12层父节点，通过类名特征（`.cell-main`、`.bitable-cell`、`[data-cell-id]` 等26种选择器）识别单元格容器
- 文本提取：优先匹配 `.cell-value` 等专门文本容器（14种选择器），fallback 到 TreeWalker 深度文本节点遍历

**引擎B：Canvas 引擎（电子表格 sheets）**
- 适用场景：飞书电子表格（/sheets/、知识库嵌入 ?sheet=），整个表格绘制在单个 `<canvas>` 元素上，单元格非 DOM 节点
- 核心算法：点击触发 + 公式栏间接读取
- 点击 canvas 后等待飞书渲染选中状态（100ms），从公式栏/编辑框（DOM 元素）间接读取单元格内容
- 自动排除单元格地址框（E231、A1 等地址格式过滤），精准获取文本内容
- 支持 `textarea`、`input`、`[contenteditable]`、`[class*="formula-bar"]` 等20+种编辑框选择器

#### 多选区域拖动复制：
- mousedown 记录起始坐标和时间，mouseup 计算拖动距离和持续时间
- 移动距离 > 8px 且持续 > 100ms 判定为拖动选择
- 拖动结束后设置 `dragJustEnded` 标记，500ms 内的 click 事件直接跳过，避免单击复制覆盖多选结果
- 模拟系统 Cmd+C 触发飞书原生复制，再读取剪贴板解析多行内容（制表符分列、换行分行）

#### 设计要点：
- **事件捕获阶段监听**：使用`addEventListener(..., true)`在捕获阶段拦截click事件，优先级高于飞书页面自身逻辑
- **双剪贴板兼容**：优先使用现代`navigator.clipboard.writeText`，失败降级到`document.execCommand('copy')`
- **防抖冷却**：250ms冷却期防止重复触发
- **用户反馈**：注入Toast组件，复制成功/失败即时反馈
- **全形态覆盖**：支持独立电子表格、多维表格、知识库嵌入表、文档嵌入表等所有飞书表格形态

#### 技术难点解决：
飞书电子表格采用纯 Canvas 渲染，单元格非 DOM 节点，传统 DOM 选择器方案完全失效。因此设计了**双引擎适配架构**，通过检测点击目标是否为 canvas 元素自动切换引擎，兼容飞书全系列表格产品。

### 2. 系统级事件触发模块
**Mac实现**：Hammerspoon `hs.eventtap.new`
**Win实现**：AutoHotkey `Hotkey`命令

#### 设计要点：
- **全局钩子**：无需目标窗口前台激活，任意位置按下侧键即可触发
- **多键支持**：同时支持鼠标侧键(3/4/5号键)、中键、自定义快捷键作为触发方式
- **防抖机制**：1秒冷却期防止误触多次执行
- **状态校验**：触发时校验运行状态、URL配置、剪贴板内容，提前给出用户提示

### 3. Chrome浏览器自动化模块
**Mac实现**：AppleScript 控制 Chrome
**Win实现**：Win32 API + Chrome键盘模拟

#### Mac端AppleScript核心逻辑：
```applescript
# 双层循环遍历所有Chrome窗口和标签页
repeat with w in windows
    repeat with t in tabs of w
        # 关键词模糊匹配URL
        if (URL of t) contains "[keyword]" then
            # 激活标签+提到最前
            set active tab index to ti
            set index to 1
            return "ok"
        end if
    end repeat
end repeat
# 未找到则新建标签页
make new tab with properties {URL:"[fullUrl]"}
```

#### 设计要点：
- **模糊匹配**：关键词无需完整URL，只要是URL子串即可匹配，适配动态路由参数
- **自动降级**：找不到已打开标签页时自动新建标签页导航，用户无需提前打开目标页面
- **加载等待**：新建页面等待3秒加载，已有标签页等待0.6秒，平衡速度和稳定性
- **错误捕获**：AppleScript执行错误时弹出明确提示，而非静默失败

### 4. 输入模拟模块
**核心流程**：点击坐标 → 等待聚焦 → 发送粘贴快捷键
**延迟参数**：点击后等待250ms再粘贴，确保输入框聚焦完成

#### 设计要点：
- **绝对坐标定位**：相对于全屏的绝对坐标，简单可靠，不依赖窗口位置变化（输入框相对于窗口位置固定）
- **持久化存储**：
  - Mac：使用系统偏好设置`hs.settings`，key格式为`fa_[url]`
  - Win：使用ini文件，key为URL哈希
- **多配置隔离**：不同目标URL分别记忆坐标，切换网站无需重新配置

**Win**：Tray 系统托盘图标

## 为什么不用其他方案？

### 为什么不用 Selenium/Puppeteer？
1. 需要启动独立Chrome实例，无法和用户正常使用的浏览器会话共享登录状态
2. 需要下载对应版本ChromeDriver，环境配置复杂
3. 无法监听鼠标点击飞书单元格的用户操作（需要反向注入通信）
4. 资源占用大

### 为什么不用 UI 自动化框架（如PyAutoGUI）？
1. 需要安装Python环境和一堆依赖，分发包体积上百MB
2. 热键响应延迟高，Python事件循环~100ms级别
3. AppleScript/Win32 API调用需要桥接，稳定性差

### 为什么这个方案最优？
1. **Hammerspoon/AHK都是系统级自动化工具**：直接使用系统API，事件回调是原生级延迟<10ms
2. **内存占用极低**：Hammerspoon常驻<30MB，AHK<5MB
3. **安装包体积极小**：整个项目包括Chrome扩展不到100KB
4. **和用户浏览器无缝集成**：不需要额外启动浏览器，用户正常使用即可
5. **稳定性高**：坐标定位+系统级输入模拟，不依赖页面DOM结构变化（只要输入框位置不变就一直能用）
